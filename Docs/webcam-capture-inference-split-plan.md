# 웹캠 캡처·추론 분리 구현 계획

## 1. 목표와 범위

웹캠은 캡처만 수행하고, MediaPipe 추론은 전용 백그라운드 스레드에서 실행합니다. ECS 반영은 메인 스레드에 유지합니다.

이번 변경의 완료 조건:

- 메인 스레드에서 DetectForVideo()를 실행하지 않는다.
- 같은 (CaptureEpoch, CaptureId)를 같은 tracker에 중복 제출하지 않는다.
- 추론 중인 입력과 완료된 결과를 다른 스레드가 덮어쓰지 않는다.
- Reset·비활성화·Play Mode 종료 시 이전 결과 게시나 해제된 메모리 접근이 없다.
- 기존 손·얼굴·포즈 표시와 Depth의 캡처 대응 관계를 유지한다.

현재 씬의 전용 Hand + Holistic 구성은 우선 유지합니다. 스레드 분리와 모델 선택 변경을 동시에 하지 않아 성능·품질 변화를 구분합니다.

---

## 2. 변경 후 구조

```text
메인 스레드
  WebcamFrameProvider
    ├─ WebCamTexture / 배경 텍스처
    └─ 최신 픽셀 + CaptureStamp
           │
           ├─ HandFrameProvider ─────→ Hand 전용 워커
           ├─ HolisticFrameProvider ─→ Holistic 전용 워커
           └─ DepthFrameProvider ────→ 기존 추론 경로 유지

각 MediaPipe 워커
  입력 소유 → 전처리 → 네이티브 추론 → 완료 결과 게시
                                          │
메인 스레드                               ↓
  각 FrameProvider → 결과 수신 → 기존 ECS 싱글턴 갱신
```

Face·Pose 단독 프로바이더도 같은 제출·수신 규칙으로 전환합니다. 비활성 tracker의 워커는 생성하지 않습니다.

### Job System의 역할

이번 변경에서는 MediaPipe 호출을 IJob으로 감싸지 않습니다.

현재 네이티브 에러 저장소가 thread_local이므로, tracker의 생성·추론·에러 조회·파괴를 한 전용 스레드에서 처리하는 구조가 명확합니다.
프레임마다 Task.Run을 호출하는 방식도 사용하지 않습니다.

픽셀 반전·리사이즈 등의 Burst Job화는 추론 분리 후 전처리가 병목으로 측정될 때 적용합니다.

## 3. 단계별 구현

### 단계 1 — 웹캠에서 손 추론 분리

변경

WebcamFrameProvider.cs에는 다음만 남깁니다.

- 카메라 시작·종료
- 새 이미지 확인 및 픽셀 획득
- VideoTexture 제공
- 해상도·반전 정보·CaptureStamp 제공

다음 책임은 새 HandFrameProvider.cs로 이동합니다.

- HandTrackingService 소유
- 손 개수 등 추론 설정
- 손 결과의 ECS 게시 및 writer ownership
- IPointSource 역할
- tracker Reset

연결 변경

- HandTrackingStatusPanel의 Reset 대상 → HandFrameProvider
- WebcamBackgroundRenderer → 기존 웹캠 참조 유지
- 손 포인트 소스 참조 → HandFrameProvider
- SampleScene.unity 및 영향받는 prefab의 컴포넌트·직렬화 참조를 함께 수정

기존 웹캠 클래스 이름과 캡처 API는 불필요하게 바꾸지 않습니다.

검증

- 손 추론을 비활성화해도 카메라와 배경 화면이 정상 동작한다.
- 손 표시·설정·Reset은 새 프로바이더를 통해 기존과 동일하게 동작한다.
- 씬에 누락된 참조나 중복 ECS writer가 없다.

### 단계 2 — 제출 규칙과 버퍼 소유권 확정

제출·수신 계약

| 동작                  | 규칙                                                    |
|-----------------------|---------------------------------------------------------|
| TrySubmit(...)        | 준비 완료·유휴 상태이며 새로운 캡처일 때만 접수         |
| Busy 상태             | 요청을 쌓지 않고 건너뜀. 다음 유휴 시점에 최신 캡처 사용 |
| TryTakeCompleted(...) | 완료 결과를 한 번만 전달                                |
| 결과 수신             | 새 카메라 이미지 유무와 관계없이 매 프레임 확인         |
| 캡처 식별             | 기존 CaptureStamp 재사용                                |
| 중복 판정             | tracker별로 (CaptureEpoch, CaptureId) 관리              |

버퍼 정책

- 카메라의 Color32[]는 메인 스레드 전용입니다.
- 제출을 수락할 때만 워커가 소유하는 재사용 입력 버퍼에 복사합니다.
- 워커 입력은 추론 완료 전까지 수정·재할당·해제하지 않습니다.
- 완료 결과는 메인 스레드가 가져갈 때까지 유지합니다.
- 입력 슬롯 1개, 완료 슬롯 1개로 시작합니다. 무제한 큐나 범용 버퍼 풀은 만들지 않습니다.

초기 구현은 재사용 Color32[]와 네이티브 호출 동안의 pinning을 유지합니다. NativeArray 전환만으로 카메라에서 무복사가 되지는 않으며,
현재 GetPixels32 비용은 갱신당 약 0.25ms입니다.

검증

- 동일 캡처를 반복 전달해도 추론은 한 번만 실행된다.
- 제출 후 카메라 버퍼를 바꿔도 진행 중 추론의 입력이 바뀌지 않는다.
- 카메라 갱신이 멈춰도 이미 완료된 결과를 수신한다.
- 해상도 변경 시 이전 입력의 사용이 끝난 뒤 버퍼를 교체한다.

### 단계 3 — MediaPipe 실행을 전용 워커로 이동

변경

Hand·Holistic·Face·Pose 서비스의 동기 SubmitAndPoll 경로를 제출·완료 수신으로 분리합니다.

tracker별로 다음 작업을 동일한 전용 스레드에서 수행합니다.

1. tracker 생성·시작
2. 픽셀 전처리
3. 네이티브 제출 및 결과 조회
4. 실패 직후 네이티브 에러 문자열 복사
5. Reset 시 tracker 재생성
6. 종료 시 tracker 파괴

메인 스레드는 EntityManager, Unity 오브젝트, UI를 계속 소유합니다. 워커는 Unity API를 직접 호출하지 않고 결과·상태·오류만
전달합니다.

구현 원칙

- 잠금은 작업 전달과 상태 전환에만 사용합니다.
- DetectForVideo() 실행 중에는 메인 스레드와 공유하는 잠금을 잡지 않습니다.
- 워커는 대기 신호를 사용하며 busy polling하지 않습니다.
- 정상 프레임 경로에서 .Wait(), .Result, Join()으로 추론 완료를 기다리지 않습니다.
- 공통화는 실제 중복되는 워커 수명주기·슬롯 관리에 한정합니다. 범용 작업 프레임워크는 만들지 않습니다.

검증

- Profiler에서 추론 구간이 메인 스레드가 아닌 워커에 표시된다.
- 추론이 오래 걸리는 동안에도 카메라 배경·UI·렌더가 갱신된다.
- tracker별 동시 네이티브 호출 수가 1을 넘지 않는다.
- 실패 시 원래 네이티브 에러 메시지가 메인 스레드에서 보고된다.

### 단계 4 — Reset·종료·Depth 연동 보존

비동기 전환에서 가장 주의할 부분입니다.

Reset

- 메인 스레드에서 결과 수신 세대를 먼저 무효화합니다.
- 진행 중 네이티브 호출을 강제로 중단하지 않습니다.
- 워커가 현재 호출을 마친 뒤 tracker를 재생성합니다.
- Reset 이전 완료 결과는 ECS에 게시하지 않습니다.

캡처 세대와 tracker 세대 구분

- CaptureEpoch는 입력 스트림의 유효성을 나타냅니다.
- tracker Reset 구분은 별도 실행 세대로 관리합니다.
- 단, 현재 손 Reset은 CaptureEpoch를 증가시켜 Depth를 무효화합니다. 이 기존 동작을 분리 과정에서 잃지 않도록 Reset 요청에서 캡처
  무효화도 명시적으로 연결합니다.

종료

```text
새 제출 차단
  → 실행 중 네이티브 호출 종료
  → 워커에서 tracker 파괴
  → 워커 종료 확인
  → 입력 버퍼·동기화 자원 해제
```

네이티브 호출의 강제 취소는 지원하지 않는 전제로 설계합니다. 종료 지연을 피하려고 tracker나 버퍼를 먼저 해제하지 않습니다.

Depth

- 기존 Depth 추론 방식은 유지합니다.
- 원본 CaptureStamp를 추론 결과까지 보존합니다.
- 비동기화로 결과가 늦게 도착해도 기존 캡처 ring·만료·세대 판정이 올바르게 작동하는지 확인합니다.

검증

- 추론 중 Reset·Disable·재활성화·씬 전환·Play Mode 종료.
- 오래된 결과 재등장, 중복 해제, 멈춤, worker 잔존 없음.
- Depth가 다른 캡처나 이전 세대의 결과와 결합되지 않음.

## 4. 검증 및 성능 비교

### 회귀 검증

기존 Tests/EditMode의 capture·timestamp·writer ownership 검증을 유지하고, 새 비동기 경계에는 다음 테스트만 추가합니다.

- 동일 캡처 중복 제출 방지
- Busy 중 입력 보존 및 결과 1회 수신
- Reset 이전 결과 폐기
- 작업 중 종료 시 안전한 자원 해제

실제 네이티브 호출과 카메라 동작은 Play Mode smoke test로 별도 확인합니다.

### 재측정 조건

기존 캡처와 동일한 카메라 설정·tracker 구성·장면에서 측정합니다. 초기화 구간과 안정 구간은 분리하고 standalone Player에서도
확인합니다.

| 지표                 | 판단 기준                                      |
|----------------------|-----------------------------------------------|
| 메인 스레드 추론 시간 | DetectForVideo가 메인 스레드에 없어야 함       |
| 평균·P95 프레임 시간  | 기존 33.47ms / 48.34ms와 비교                  |
| tracker별 결과 갱신률 | 렌더 FPS와 별도로 기록                         |
| 캡처→ECS 게시 지연    | 평균·P95 및 시간에 따른 누적 여부 확인         |
| 중복 제출            | 같은 캡처를 같은 tracker에 제출한 횟수 0       |
| 메모리               | 안정 구간에서 입력·결과 버퍼의 지속적 증가 없음 |

60 FPS 달성은 아직 보장하지 않습니다. 이번 변경의 보장 대상은 메인 스레드 차단·중복 제출·대기열 누적 제거이며, 실제 FPS와 추적
지연은 재측정으로 판단합니다.

## 5. 이번 변경에서 제외할 항목

- Holistic 손 결과로 통합: 전용 Hand와 품질 비교 후 별도 결정
- MediaPipe GPU delegate 전환: 백엔드 변경은 별도 검증 필요
- 텍스처 포인터 직접 전달·GPU 무복사: 현재 CPU 이미지 브리지와 다른 구현 범위
- 전처리 전면 Job화: 재측정에서 필요성이 확인되면 추가
- 해상도·모델 변경: 성능 비교 조건과 추적 품질을 우선 유지

구현 순서는 캡처 분리 → 버퍼·제출 계약 → 워커 전환 → 수명주기·Depth 검증 → 재프로파일링입니다.

## 6. 구현 및 검증 기록

- 웹캠의 손 추론·ECS 게시를 `HandFrameProvider`로 분리하고 씬의 손 소스·상태 패널 참조를 이전했습니다.
- Hand·Face·Pose·Holistic은 전용 `TrackerWorker`에서 네이티브 수명주기와 추론을 실행합니다. 프로바이더는 새 입력 확인 전에 완료 결과를 수신합니다.
- 세대 검사와 완료 게시를 같은 잠금에서 처리합니다. Reset 대기·실행 중이거나 완료 결과가 미수신 상태이면 제출을 거부하며, Reset 실패 시 제출을 닫습니다.
- Hand Reset은 워커 세대를 먼저 무효화합니다. 기존 CaptureEpoch 증가 연결은 유지합니다.
- Depth 반복 시각에도 Weight를 적용하며, World가 먼저 파괴된 경우 쿼리를 중복 해제하지 않습니다.
- Unity 6000.6.0f1 EditMode 관련 회귀 47개 통과. 캡처 ring·timestamp 매핑·writer ownership·ABI·Depth 보정 및 워커 동시성 검증을 포함합니다.
- 임시 네이티브 스모크: 4종 트래커의 제출·수신·중복 거부·Reset 후 재제출·종료 통과. 별도 스모크에서 카메라 픽셀이 없어도 Hand 완료가 원래 CaptureStamp로 ECS에 게시됨을 확인했습니다. 임시 코드는 실행 후 제거합니다.
- 증거: `/tmp/capture-worker-expanded.xml`, `/tmp/capture-worker-camera-smoke.xml`. 빈 64×64 입력을 사용한 EditMode 검증이며 실제 카메라 영상 품질·렌더 FPS·standalone Player 성능 측정을 대신하지 않습니다.
- 실제 카메라/Player 재프로파일링은 이 기록에 포함되지 않습니다. 60 FPS 달성이나 기존 평균·P95 대비 향상을 주장하지 않습니다.
